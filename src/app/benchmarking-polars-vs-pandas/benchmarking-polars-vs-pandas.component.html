Benchmarking Polars vs Pandas

13th December 2023

Summary

Polars is fast becoming one of my favourite Python packages to use. It offers itself as a new but hard-hitting competitor to Pandas, the de-facto data table library for Python since 2008, spruiking features like built-in parallelisation, query optimisation, significant performance improvements over Pandas, strict typing and immutability for columns - to name its most impressive qualities thus far.
After hearing the pitch and trying the library in my own work instead of Pandas, I was sold. The next step, was to get the people I work with on board as well, and this is a bit more tricky. Introducing a new package to a team - especially one which attempts to be a replacement for an existing package, can invoke a healthy amount of scepticism. Great that it's selling us these improvements over what we already use, but what about the many other considerations we need to take that aren't Polars' selling points?
In this article, we'll walk through my main considerations when evaluating whether or not a package should be included into the project or not - which means we'll be looking at more than just performance.
  • Performance
  • Syntax
  • Functionality
  • Ecosystem
  • Conclusion

Syntax

Most people learning Polars for the first time are coming with experience from Pandas, so ideally Polars needs to offer benefits to its syntax as compared to Pandas - which it does. The table below compares various aspects of the syntax of both Pandas and Polars.
Feature Pandas Polars
Style
Pandas code tends to prefer one line per expression. If you're adding three new calculated columns, each gets their own line, assigning a new column to the existing dataframe. There is also frequent use of mutating existing dataframes, and the canonical way of adding columns to a dataframe uses this.
Polars code tends to prefer longer, chained expressions. Adding three new calculated columns is done as separate lines within a larger .with_columns() method, which can be chained with other method and returns a new dataframe object, distinct from the initial dataframe.
Immutability
Pandas objects are mutable, so it is possible to make changes to a data table without explicitly creating a new copy or instance. This adds flexibility in how users are able to write code, but at the cost of making it difficult to tell when a table has or hasn't been changed by only reading through code.
Polars objects are immutable, so values can only be adjusted by creating a new instance of the object to be mutated. This is beneficial for maintainability, but also due to how Polars works under the hood, does not incur significant additional memory cost.
Interpretability
For the most part, Pandas code is easy to follow and make sense of. The difficulty arises when using more sophisticated features, including dealing with indexes and multi-indexes, and the use of the .transform() method.
After the initial jump of learning Polars' expression syntax (one aspect which is very different from Pandas), there's nothing much else in Polars which is significantly difficult to figure out, besides looking up the precise definitions of specific methods, such as .with_row_count()
Consistency
Pandas suffers from being a large library for a long time, in that a lot of different syntax has been added throughout time and is still supported, and this can very easily lead to inconsistency in writing code. Take for example, the argument of the .agg() method - there's at least three different possible types for the argument, depending on whether it was called on a Series of DataFrame object, and some argument types allow more functionality than others.
Polars has a much cleaner and consistent syntax for all operations you can think of, and everything fits into the predominant style of chained expressions. This is perhaps not a surprise, as Polars is able to learn from the mistakes of Pandas' syntax, and also frequently updates to keep its syntax towards its intended style.
Modularity
As with most programming languages, you're able to use the power of abstracting logic to functions, conditional statements, and all of that to efficiently write code. However, Polars takes this a step further...
Polars support lazy execution of queries, as well as automatic query optimisation. This means, if you want to abstract code into functions, you can have your functions return LazyFrames, which can be executed only when required, and automatically performs query optimisation so the resulting performance can be faster than if the individual queries were executed one at a time.

Functionality

We've seen that Polars performs better than Pandas, and that the syntax is also better to work with, but can it do everything that Pandas can? Naturally, both libraries have a lot of common functionality, so we're only going to cover significant differences in capabilities between the libraries here.
Feature Pandas Polars
Native Parallel Processing
Pandas is only single-threaded natively, but can be parallelised using other libraries (e.g. multiprocessing, dask, modin, etc.)
Polars runs queries across all available CPU cores by default.
Query Optimisation
Polars introduces syntax for lazy execution of queries, which automatically performs query optimisation before executing the query.
Built-in plotting
Pandas comes with an installation of matplotlib and the .plot() convenience function, without needing the boilerplate of a typical matplotlib plot.
Arbitrary datatypes in DataFrames
Values in Pandas dataframes can take arbitrary values (with the object column type, though it is dubious to want to allow completely arbitrary values).
Only supported datatypes are allowed (though homogenous lists and heterogenous structs are both supported).
Specialised support for list/array columns
Pandas has minimal functions to deal specifically with list types, specifically .explode(), and otherwise with .apply() and .transform() without optimisations.
Polars has extensive methods to handle list columns, and basic support for array and struct types. Arbitrary Python code can be executed with .apply() and .map_groups().
Executing SQL
Polars can execute SQL queries on DataFrames (unsure how useful this is - but it exists).
Index columns
Polars does not use index columns like Pandas does - instead such columns are treated as any other column.

Ecosystem

Whichever library you use, you'll likely not be using them in isolation, but alongside other libraries. Let's finish off by having a look at how each library interacts with the wider Python and software ecosystem.
Consideration Pandas Polars
Plotting and Charts
Most major Python charting libraries have native support for Pandas.
So far, only Plotly has native support for Polars, and other libraries can be used simply by using .to_numpy() or .to_pandas() first.
Scikit-Learn
Most functions can accept Pandas DataFrames as input, but only some return results as DataFrames.
Most functions require conversion using .to_numpy() on input, then casting back to Polars if required with pl.DataFrame(). This isn't the most concise way for the libraries to interface, but is very effective.
Geometry
Via GeoPandas.
Via GeoPolars.
Maturity
Released in 2008, and nowadays still the standard for tabular data in Python. From PyPI stats, 146,000,000 downloads in the last month.
Released in 2021. From PyPI stats, 2,700,000 downloads in the last month.
StackOverflow/GitHub Support
As the de-facto Python library for tabular data, there is abundant support online. 40,000 stars on GitHub.
At the time of writing, around 1500 related questions on StackOverflow, and just generally from experience, there is sufficient support from the community to assist learning and debugging. 21,000 stars on GitHub. Issues raised on GitHub are also addressed quickly, from experience.
Sponsorship
Pandas is sponsored by the NumFOCUS US non-profit organisation as well as in-kind and contributor support from various other institutions and organisations.
Polars is sponsored by JetBrains, and in August 2023 received US$4 million in seed funding from Bain Capital Venture and individual investors.

Conclusion

Polars does indeed have aspects in which it dominates Pandas, some in which it is slightly better, and some which it is poorer.
In my eyes, the only reasons not to go with Polars are two-fold, and are related to each other.
  1. Polars is still a relatively young library, and lacks the stability that Pandas has been able to maintain. We can hope that future updates to Polars continue to build on its functionality in a way that the community supports, but we can't assume this like we can with Pandas.
  2. Because Polars usage is still growing, the amount of community support (such as on StackOverflow) is still small compared to Pandas, and especially if you're a less experienced programmer trying to use Polars to do some more advanced, but not necessarily supported functionality, you may have better luck searching forums for help with Pandas instead.
Personally I see these two downsides as worth the massive performance, syntax and functionality improvements which Polars offers, so at least for myself, I know what library I'll be relying on moving forward for my Python data table needs, and I hope that the information presented here as also helped you to understand which is the better solution for your use case.
